    Answers to the RFC's three questions¶

    1. End date: "run date − 2 days" against PLAN § S6 "to yesterday". The frozen code makes a GDELT day final only after file-day d+1 (extract_gdelt.py:97-98). With "yesterday" the closing file-day would be today's, which is partial at 02:37 UTC. The result is the exact defect of the pinned 10-26 row (finding 1), and the incomplete flag would not show it (122). So "to yesterday", read literally, cannot be "the same procedure as S1" for GDELT without reproducing an undercount. For USGS and markets "yesterday" is technically available. This changes the plan's wording, so it is class B, options below (B-2). Whatever the option, the end date must be in UTC (finding 10). "Nothing is lost" holds for the days left out only if the next month's start covers them (finding 3).

    2. USGS overlap criterion: byte-equality of rows or equality of daily counts. The frozen procedure produces both files from one query (extract_usgs.py:43-51). events.csv is not a by-product: it is the H3 input (protocol USGS.angular). A count-only criterion would let revised times and coordinates through. Byte-equality will probably block every month, given an extraction on 2026-10-27 08:43 UTC (finding 4). This changes the overlap criterion, so it is class B, options below (B-3). Under any option, the action on failure must be written before the first run, not chosen by the researcher after seeing the differing rows.

    3. Location of extend_s6.py. scripts/, as the RFC proposes. council/PIN.md:8 already provides for "a new file there only through an accepted RFC", D10 covers it, and the file produces study data, which council/scripts/ should not. The condition is finding 11: its hash is recorded with every extension, and it changes only by RFC.

    Revisions and "nothing is lost" / "rows recoverable later"¶

    Under the RFC a prospective row is extracted once, appended, and never revisited (§ 4). Each source behaves differently:

    • GDELT. Export files do not change once published, but their availability does. A file that is 404 or erroring at extraction time is frozen into the row as "missing", and the day's n is lower. The pinned 10-26 row is the first instance (finding 1), and E6 showed two more (finding 5).
    • USGS. Magnitudes, times and coordinates are revised for weeks. An event can cross 5.5 in either direction after the row is appended, which changes n in daily.csv and the H3 input in events.csv.
    • Markets. A revised close C_d changes y_d and y_{d+1}. Because the frozen code downloads the full history, the next month's run sees the revision. Under byte-equality, that blocks the merge.

    So "recoverable later" holds only for rows never extracted. A row already appended is either frozen at its first vintage (if later overlaps do not cover it) or blocks every later merge (if they do, under byte-equality). The protocol has no rule on which vintage S7 reads. This is class B (B-4).

    Class B options (the PO chooses; the Critic does not)¶

    • B-1 (finding 1): the pinned GDELT row 2026-10-26.
    • (a) Keep it as pinned (PIN as written). The overlap compares 10-21..10-25 only, 10-26 is a declared, counted deviation in the prospective set, and the S1 journal's "S6 will re-extract it" is withdrawn on the record.
    • (b) Allow S6 to replace that single row with the re-extraction. This is a change inside the pin (PIN.md:23, class B), recorded as a post-freeze entry with both values kept.
    • Either way, decide before the first run.
    • B-2 (question 1): end date.
    • (a) Plan wording "to yesterday" kept, all arms. GDELT reproduces the partial-closing defect.
    • (b) Common end = run date − 2 days, UTC (the RFC). The plan's wording is amended.
    • (c) GDELT run date − 2, USGS and markets "yesterday". The arms end on different days.
    • B-3 (question 2 and markets): overlap criterion and the action on failure, declared before the first run.
    • (a) Byte-equality of every overlap row, daily.csv and events.csv (the RFC). Any difference blocks the arm.
    • (b) Equality of daily counts blocks. events.csv differences are reported, not blocking.
    • (c) Byte-equality required only on days older than a declared lag. Younger days are reported.
    • For each: whether a failure means "no merge this month" or "merge the new rows and record the differences".
    • For markets, the same choice over the full-history overlap.
    • B-4 (revisions): which vintage of a prospective row S7 analyses.
    • (a) First extraction, frozen. Later differences are recorded only.
    • (b) A single re-extraction of the whole prospective period at a date fixed now, before UNSEAL-prospective, replacing the appended rows.
    • (c) Each day extracted once at a fixed lag after its date.
    • This must be fixed before 2027-04-27. It touches the S7 gate (night item 8).

    Verdict¶

    GO with conditions. Each condition is to be met in a revision of the RFC before the PO accepts it; the Critic verifies the revision.

    1. The PO decides B-1 before any run, and the RFC's overlap and cross-check follow that decision (finding 1).
    2. The wrapper specification states that sys.argv is replaced before the GDELT main() and that OUT folders are created (findings 2, 8).
    3. The RFC specifies month k: a per-month work folder, the start rule per arm, a cut-off at s6_cursor.last_extension, and the treatment of rows appended in earlier months (finding 3).
    4. The overlap criterion and the action on failure are the PO's B-3 choice, written in the RFC before the first run, with no case left to a post-hoc researcher decision (finding 4).
    5. The completeness check reports errors separately from 404s per file-day, for both places of execution (finding 6).
    6. The extension manifests record the real window, the wrapper's and the frozen modules' sha256, and the place of execution with its run or session identifier (findings 7, 11, 12).

    Recommended answer for D12: yes to the method, but not to the RFC as written: accept a revision that meets conditions 1–6, after the PO has chosen B-1, B-2 and B-3 (B-4 before 2027-04-27), and only after the Critic has verified that revision.
